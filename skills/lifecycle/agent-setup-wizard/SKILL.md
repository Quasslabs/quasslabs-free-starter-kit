# SKILL: agent-setup-wizard

**Bot:** operator · any  
**Role:** Single entry point for setting up a new agent or automating a task. A coworker describes what they want to build; the wizard loads the core skill kit (24 foundational skills), discovers relevant tech-specific skills, sets Ug-ug mode per skill, wires in MindPalace + GStack at the right layer, writes or updates the Operator routing config, recommends rate limits and log formats, and outputs a CLAUDE.md draft ready to use. Run this before writing any code.  
**Ug-ug mode:** full  
**Model:** opus - high-stakes judgment or architecture trade-offs required
**Tool compatibility:** Claude Code · Codex · Cursor · Cowork
**Status:** beta
**Parallelizable:** conditional - yes if each run targets a separate project root; no if two runs scaffold the same root concurrently

---

## Model

**Verdict:** `sonnet` — multi-phase agent setup requires reasoning across competing constraints and drafting configuration outputs.

| Tier | Pick | Notes |
|---|---|---|
| Cloud | sonnet | Reasoning + drafting across phases; intake, skill discovery, config generation |
| Local (installed) | qwen2.5:7b | General reasoning; adequate for structured setup phases |
| Local (ideal) | qwen2.5:72b (not installed) | Full reasoning capability for complex multi-phase setup |

- "I want to build an agent that does X"

## Phase 3 — Skill discovery (intent-match the initial prompt)

Intent-match the user's stated task/build description against the hub (the logic
formerly in `skill-recommender`, now folded into `skillmaster` Step 0.5). Check:
1. Core skills already selected (from Phase 2)
2. Tech-stack-specific skills not in core kit
3. Existing skills in `skills/` and `ready\` (rank by intent overlap with the prompt)
4. **Runners** — `<routines>/ROUTINES-INDEX.md` (any existing automation matching the task)
5. Items of note repos (`<notes>/...`)
6. Flags gaps (skills that don't exist yet → note for skillmaster Step 0.5 build)

Output: ranked tech-specific skill + runner list with match rationale, seeded from
the initial prompt/context (core skills are not re-listed). This is the project-seed
counterpart to `chat-primer` Phase 1.5a's per-session discovery.

If no additional skills match: proceed with setup scaffold using only core skills.

## Phase 4 — Ug-ug level assignment

**Core skills** — Ug-ug levels are pre-assigned from `CORE-SKILL-KIT.json`. Do NOT override them:
- Plans (strategic decisions) use **ultra** compression
- Internal reasoning (debug/analysis) use **full** compression  
- User-facing responses use **none** (normal prose)

For **additional tech-specific skills** discovered in Phase 3, assign the correct Ug-ug mode:

| Skill type | Ug-ug level | Rationale |
|---|---|---|
| PM/client-facing output (briefs, reports, proposals) | `none` | Full prose needed |
| Internal reasoning + structured output | `lite` | Most skills |
| Build/deploy/test pipelines | `full` | Max compression |
| Log-watcher, Lambda ops, real-time alerts | `ultra` | Machine-readable only |

**Auto-assignment rules:**
- If skill writes to a file a human will read → `none`
- If skill calls another skill or routes sub-agents → `lite`
- If skill runs `terraform`, `aws`, `docker`, or `git` commands → `full`
- If skill processes CloudWatch events, SQS, or EventBridge → `ultra`

Output per added skill:
```
transcript-research   → lite   (internal reasoning, feeds ballpark)
slack-crud            → full   (API calls, no prose needed)
fathom-sync           → ultra  (ETL, machine output)
output-composer       → none   (PM reads the brief)
```

**Note:** All core skills have their ug-ug levels already set. Combined ug-ug application:
- Plans: all core ultra + tech-specific as assigned
- Internal reasoning: all core full + tech-specific as assigned
- User responses: all core none + tech-specific as assigned

## Phase 4.5 — Ug-ug ultra enforcement

Regardless of individual skill ug-ug levels, enforce these project-wide defaults in the CLAUDE.md output:

```
Plans / strategic decisions:     ULTRA  (bullets + symbols, zero narrative)
Internal reasoning / debug:      ULTRA  (telegraphic, abbreviate freely)
TodoWrite / handovers / LESSONS: ULTRA  (bullets + tables, no prose wrap)
Code output:                     NO CHANGE  (clean + readable)
User chat responses:             NORMAL PROSE  (clear communication)
```

These defaults OVERRIDE any per-skill ug-ug level. They are written into the project CLAUDE.md under `## Ug-ug mode` and cannot be downgraded.

Banned openers (hard enforcement — write into CLAUDE.md):
```
Let me · I'll go ahead · I need to · Certainly · Sure! · Great! · Of course
I'll now · Also need to · In order to · This will · Let me explain
```

## Phase 6 — Model routing (GStack)

Assign the right model to each step in the skill pipeline. GStack levels:

| Model | Use when | Approx cost per 1k calls |
|---|---|---|
| `claude-haiku-4-5` | Formatting, simple extraction, routing decisions, ETL | ~$0.25 |
| `claude-sonnet-4-6` | Reasoning, drafting, code generation, research | ~$3.00 |
| `claude-opus-4-6` | Architecture decisions, complex multi-step reasoning, sensitive judgment | ~$15.00 |

**Auto-assignment rules:**
- Step is deterministic (format, convert, route, classify from fixed list) → Haiku
- Step requires understanding context or generating content → Sonnet
- Step requires judgment across competing constraints or architectural decisions → Opus
- If in doubt → Sonnet (good default; cheaper to start, upgrade if quality low)

Output per step:
```
Step: extract screen list from storyboard    → haiku   (structured extraction)
Step: generate screen HTML content           → sonnet  (content generation)
Step: decide EC2 vs AgentCore architecture   → opus    (architecture judgment)
Step: format billing report markdown         → haiku   (deterministic format)
Step: fuzzy-match Jira actuals to estimates  → sonnet  (semantic matching)
```

For every API endpoint or scheduled trigger in the plan, specify:

- Dev / experimental: 5
- Production, single user: 10–25
- Production, multi-user: 50–100

### Log format
All Lambdas in the plan should use the structured logger from `aws-account-bootstrap`:
```python
from common.logger import log
log("info", "step_started", step="transcript-research", job_id=job_id)
log("info", "step_complete", step="transcript-research", duration_ms=1420)
log("error", "step_failed", step="market-research", error=str(e))
```

Log events to always capture:
- `job_started` — input params (no PII)
- `cache_hit` / `cache_miss` — fingerprint, type
- `llm_called` — model, input_tokens, output_tokens, duration_ms
- `step_complete` — step name, duration_ms
- `job_complete` — total duration, run_cost_usd
- `error` — step name, error message, job_id

## Workflow orchestration

<!-- Apply these rules on every non-trivial task (3+ steps or architectural decisions) -->

- **Plan first.** Enter plan mode before any task with 3+ steps. Write plan to `tasks/todo.md`.
- **Subagents for research.** Offload exploration, web research, and parallel analysis to subagents. One task per subagent.
- **Self-improvement loop.** After any user correction: update `LESSONS.md` with the pattern. Review lessons at session start.
- **Verify before done.** Never mark a task complete without proving it works. Ask: "Would a senior engineer approve this?"
- **Demand elegance.** For non-trivial changes: pause and ask "is there a more elegant way?" Skip for obvious fixes.
- **Autonomous bug fixing.** When given a bug report: fix it. Point at logs/errors. Zero context-switching required.
- **/careful before destructive commands.** Any `rm`, `DROP`, force push, or migration requires explicit confirmation.
- **Compact at ~50% context.** Manual compact when context window is half full.

Full workflow (Think→Plan→Build→Review→Test→Ship→Reflect): see `skills/gstack/SKILL.md`

## Operating principles

<!-- Mandatory header on every project CLAUDE.md.
     Concept inspiration only (NOT a code source): the *idea* of declaring per-tool operating principles was
     observed in codeaashu/claude-code + yasasbanukaofficial/claude-code, which appear to host leaked
     proprietary Anthropic source. We do NOT clone, vendor, import, run, or copy prompts from those repos.

1. **Study existing patterns before modifying.** Read the surrounding code. Match what's there before introducing new shapes.
2. **Keep changes small and reviewable.** One concern per commit. If a change touches more than ~5 files, split it.
3. **Match existing style/naming conventions.** Don't introduce camelCase in a snake_case file. Don't introduce a new lint config.
4. **Validate early; explain what can't be tested.** Run the smallest meaningful check before claiming done. If something can't be tested locally, say so explicitly.
5. **Favour readability over cleverness.** Optimize for the next human reader.
6. **Declare what you conflict with.** Every skill declares `**Parallelizable:** yes | no | conditional`. Honor that when chaining.
